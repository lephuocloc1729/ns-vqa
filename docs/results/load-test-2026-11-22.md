# Load test, 2026-11-22 (plan item 3.2)

GitHub Actions run 45039020561, workflow `.github/workflows/load-test.yml`, Locust file
`eval/load/locustfile.py`.

## Setup

- **Stack:** the Docker Compose stack (nginx → API → Postgres), with the **fake pipeline**. No Claude calls, so the numbers measure our own system.
  - A fake answer takes about 0.96 s: perception and parsing 0.12 s each, then the writer streams 6 pieces 0.12 s apart.
  - It streams the same events as a real answer.
- **API processes:** `API_WORKERS` = 1, 2 and 4, one runner each.
- **Machine:** GitHub `ubuntu-24.04` runners with 4 vCPUs and 15 GB RAM. They had AMD EPYC 9V74 CPUs for 1 and 2 workers, and an EPYC 7763 for 4 workers. Locust ran on the same machine.
- **User behaviour:**
  - opens the page and starts a session;
  - then waits 5–15 s between actions;
  - actions are weighted 3 : 2 : 1 : 1: ask a question with a photo (reading the whole SSE stream), reload the history, open an earlier answer, check `/health`.
- **Capacity profile:** 10, 25, 50, 100, 200, 300, then 500 users, 60 s each, users starting at 20 per second.
- **Stress profile:** 100 users, then 1000 for 120 s, then 20 for 60 s.

## The main finding: each API process answers one question at a time

The rule engine keeps one scene per Prolog process, so the API runs one answer at a time per process. Answer throughput is therefore about `workers ÷ answer time`, and extra users wait in a queue.

| API processes | max answers/s (measured) | in theory (1 / 0.96 s × processes) |
|---:|---:|---:|
| 1 | 1.05 | 1.04 |
| 2 | 2.08 | 2.08 |
| 4 | 3.48 | 4.17 |

With 4 processes the gain falls short of linear. The server hands each new connection to a process whether it is busy or not, so some answers wait behind a busy process while another is idle.

**The knee.** With p95 under 10 s (ten times one answer) as the limit, the system holds about:
- **25 users** with 1 process;
- **50 users** with 2;
- **50 users** with 4. With 4 processes, p50 stays under 10 s up to 200 users, but p95 is pulled up by the uneven routing.

## What stays fast at every load

- **The first stream event:** p95 under 100 ms at every step, up to 1000 users. A queued question gets its turn id and "started" status at once, and the UI shows the waiting stage.
- **History and `/health`:** p95 at most 120 ms at every step, up to 1000 users.
- **Failures: 0** in every step of every run, including 1000 users at once. Nothing timed out, crashed or returned an error. Overload shows as waiting, never as errors.
- **Throughput:** the busiest step served 29 HTTP requests per second (4 processes, 1000 users). That is set by the users' think time, not by a server limit: no endpoint other than answering slowed down.

## Stress and recovery

In this run the stress test followed the capacity ramp on the same API.
- The API finishes and stores every answer it accepted, even when the user has left (so the user can reopen it from History).
- So the backlog from the ramp carried over into the stress test.
  - With 1 process, no answer finished during the stress test.
  - With 1 and 2 processes, the "recovery" step at 20 users still waited 98–180 s, which was the backlog draining.
- The workflow now restarts the API between the two tests, so the next run measures stress from an idle API.

With 4 processes (the least backlog), the stress test served 355 answers at 1000 users (p50 52 s, p95 85 s) with no failures.

## What this means for the real system

- A real answer takes about 20 s, almost all of it waiting on Claude.
- With one process, the server finishes about **3 answers a minute** in total. A UAT with 5 people asking at the same moment would make the last one wait about 100 s.
- Fix: run several pipeline processes (about 150–300 MB of RAM each; the VPS has about 3 GB free).
  - The best way is one API process that hands each question to the first *free* pipeline process. That avoids the uneven routing seen with 4 processes, and keeps one spend count and correct metrics.
  - `API_WORKERS` (several API processes) works too, but the spend cap and the Prometheus counters then count per process.
